# TaihuCasino 两人团队开发计划 v1

状态：执行版  
日期：2026-04-09  
适用对象：TaihuCasino 两人团队

## 1. 计划目标

本计划用于把当前静态原型仓库推进为一个可上线实验的 web game 版本。

首轮目标不是做成完整商业产品，而是完成一个具备以下能力的 MVP：

- 统一赌场大厅入口
- 四个核心玩法可进入、可游玩、可结算
- 会员注册登录可用
- 用户基础资料、钱包与游戏进度可保存
- 激励广告与 IAP 形成最小可验证闭环
- 数据事件可记录，支持首轮实验与复盘

## 2. 当前基础

当前仓库已经具备以下基础：

- `index.html` 作为统一首页入口
- `pages/member-counter.html` 作为会员注册柜台
- `pages/baccarat.html`
- `pages/roulette.html`
- `pages/dice.html`
- `pages/blackjack.html`
- `assets/js/member-auth.js` 作为 Auth0 前端会话基础
- `docs/太湖赌场产品宪章_正式版_v1.0.md` 作为最高产品原则文件

当前仓库仍然存在的主要问题：

- 多个玩法页面尚未接入统一账户、钱包和保存逻辑
- 页面之间的公共状态尚未抽象为共享模块
- `baccarat2.html`、鸡尾酒相关页面仍属于内容分叉或补充体验，尚未纳入 MVP 主线
- 当前仓库仍然更接近“原型集合”，还不是“统一产品”

## 3. 本轮技术决策

首轮开发默认采用以下技术路径：

- 登录认证：Auth0 SPA
- 会员入口：`pages/member-counter.html`
- 云端数据：Supabase
- 前端形态：静态多页站点 + 公共 JS 模块
- 首轮玩法：百家乐、轮盘、骰子、21点
- 首轮变现：激励广告 + 小额 IAP

以下内容不进入首轮 MVP：

- 复杂会员成长系统
- 多人对战
- 赛季制内容
- 社交系统
- 大量商城商品
- 高复杂度 AI 或玩法变体扩展

## 4. 产品交付标准

首轮 MVP 必须满足以下标准：

### 4.1 统一大厅

- 首页不再只是原型导航页，而是产品大厅入口
- 会员状态、入口导航、玩法跳转、钱包信息应具备统一表达
- 未登录用户进入受保护玩法时，应被引导至会员柜台

### 4.2 四个玩法

四个玩法都应满足：

- 可进入
- 可完成至少一轮完整游玩
- 有统一结算
- 能影响统一钱包余额
- 能记录基础统计
- 能保存最近状态并恢复

### 4.3 会员系统

会员系统首轮至少包含：

- 注册 / 登录
- 会话恢复
- 登出
- 基础用户资料
- 会员状态展示
- 最近登录与最近游玩摘要

### 4.4 保存与同步

至少支持保存以下数据：

- 用户资料
- 钱包余额
- 基础玩法统计
- 最近游玩状态
- 关键偏好设置

云端数据为主，本地缓存为快速恢复辅助。

### 4.5 变现闭环

首轮变现只做最小验证版本：

- 激励广告至少覆盖奖励领取与失败恢复两个场景
- IAP 只上少量标准商品
- 所有奖励、扣费与到账必须经过统一钱包逻辑
- 不允许出现任何“必胜”“保底翻盘”“现金收益幻觉”类设计

## 5. 分阶段开发计划

## Phase 0：项目收敛与底座锁定

目标：从“页面集合”收敛到“统一产品结构”。

交付：

- 确认 `member-counter.html` 为唯一会员入口
- 确认 `index.html` 为统一大厅入口
- 确认首轮主玩法页为：`baccarat.html`、`roulette.html`、`dice.html`、`blackjack.html`
- 明确 `baccarat2.html` 为候选或归档页，不进入主线
- 盘点各页面现有功能、状态与差异
- 明确公共 CSS、公共 JS 与页面专属脚本的边界

完成标志：

- 团队可以清楚回答“哪些页面属于 MVP 主线，哪些不属于”
- 后续功能不再直接散落到各 HTML 页面中各自为政

## Phase 1：大厅 MVP 与前端统一状态

目标：形成可走通的统一用户流。

交付：

- 首页进入大厅化表达
- 统一导航与会员入口
- 公共会话状态接口
- 公共钱包状态接口
- 公共访问守卫
- 公共事件埋点接口
- 四玩法页面都能读取统一用户上下文

完成标志：

- 用户能从首页进入会员柜台，再进入大厅，再进入任意玩法，并保持统一状态

## Phase 2：Auth0 + Supabase 账户与保存闭环

目标：把登录、资料、钱包、进度接成真实数据链路。

交付：

- Auth0 登录、回调、登出、会话恢复完整可用
- Supabase 用户表、钱包表、进度表、事件表、购买表、广告奖励表就位
- 首次登录初始化资料与钱包
- 已登录用户可从云端恢复基础状态
- 本地缓存与云端同步策略落地

完成标志：

- 用户刷新页面或切换设备后，能恢复自己的基础资料与钱包、玩法进度

## Phase 3：四玩法统一接线

目标：让四个玩法真正接入统一产品系统。

交付：

- 百家乐接入统一钱包与保存
- 轮盘接入统一钱包与保存
- 骰子接入统一钱包与保存
- 21点接入统一钱包与保存
- 每局记录开始、结算、输赢、余额变化
- 每个玩法完成后可返回大厅

完成标志：

- 四个玩法都能完整形成“进入、游玩、结算、保存、返回”的闭环

## Phase 4：广告与 IAP 闭环

目标：验证变现可行性，但不破坏产品宪章。

交付：

- 激励广告主路径
- 广告奖励入账
- 失败恢复广告位
- 标准商品列表
- 购买成功、失败、取消处理
- 到账写入购买记录与钱包账本

完成标志：

- 广告和购买都能影响统一钱包，且事件可追踪、逻辑可回滚

## Phase 5：实验版打磨与小范围上线

目标：让产品具备真实实验条件。

交付：

- 大厅中的会员摘要
- 最近游玩信息
- 基础错误提示与空状态
- 统一加载与失败提示
- 关键指标埋点
- 首轮实验版发布清单

完成标志：

- 可以进行小范围真实用户实验，并记录核心行为数据

## 6. 核心模块设计

### 6.1 会员模块

负责：

- 登录态管理
- 用户资料读取与恢复
- 受保护访问控制
- 登出与回退逻辑

### 6.2 钱包模块

负责：

- 当前余额
- 奖励发放
- 扣费结算
- 失败回滚
- 云端同步

### 6.3 存档模块

负责：

- 玩法进度读取
- 最近状态保存
- 本地缓存恢复
- 云端权威数据同步

### 6.4 事件模块

负责记录：

- 登录 / 登出
- 开始对局 / 结束对局
- 广告完成 / 广告失败
- 购买成功 / 购买失败
- 恢复补贴

### 6.5 页面约束

所有玩法页必须遵守以下约束：

- 不单独维护自己的会员状态
- 不单独维护自己的余额体系
- 不绕过公共保存接口直接写业务状态
- 不直接生成与宪章冲突的广告或付费逻辑

## 7. 角色分工

你负责：

- 宪章对齐
- 玩法规则取舍
- 界面与文案方向
- 广告/IAP 商品设计
- 测试反馈与版本判断

我负责：

- 技术结构收敛
- Auth0 与 Supabase 接线
- 公共状态模块
- 四玩法统一接入
- 变现闭环
- 上线准备

## 8. 周节奏建议

建议采用每周一次版本评审。

每次评审只看四件事：

1. 是否更像一个统一大厅，而不是原型拼盘
2. 是否更容易形成回访和保存
3. 是否更接近真实可实验产品
4. 是否突破了产品宪章边界

## 9. 风险与控制

主要风险：

- 四玩法并行导致收敛速度下降
- 账户、保存与变现三条线同时推进导致复杂度过高
- 广告与 IAP 接入拖慢核心玩法闭环
- 静态多页结构下公共状态同步成本上升

对应控制原则：

- 先统一底座，再接玩法
- 先保证闭环，再做打磨
- 先保证统一钱包与保存，再扩展玩法表现
- 与宪章冲突的商业化方案一律不上线

## 10. 成功标准

首轮开发完成后，应能回答“是”的问题包括：

- 用户能注册并登录吗
- 登录后能跨页面保持状态吗
- 钱包与进度能保存并恢复吗
- 四个玩法都能接入统一系统吗
- 广告和 IAP 能形成最小可验证闭环吗
- 我们能看到首轮实验所需的关键数据吗

如果上述问题存在明显否项，则本轮不视为完成。
